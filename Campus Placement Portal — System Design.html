AI-Powered Campus Placement Portal — System Design

1. Vision

A campus placement system where AI recommends, humans decide, and every decision is explainable and auditable. Differentiators beyond a standard ATS:

  • Explainable candidate–job matching (not a black-box score)
  • Personalized skill-gap analysis for students
  • "What-if" career simulation
  • Human-in-the-loop shortlisting with mandatory override reasons
  • Full audit trail for fairness and compliance

2. Tech Stack

Layer Technology
Frontend React.js + Tailwind CSS
Backend API Node.js + Express
Database MongoDB Atlas
ML Service Python (FastAPI) + scikit-learn + spaCy + Sentence-Transformers
Reasoning / explanations LLM (via API)
Auth JWT (access + refresh tokens)
File storage Cloudinary (resumes, logos, certificates)
Cache Redis (embeddings + LLM explanation cache)

3. High-Level Architecture

┌───────────────────┐        ┌──────────────────────┐        ┌─────────────────────┐
│  React + Tailwind  │ <────> │   Node.js / Express    │ <────> │   MongoDB Atlas       │
│  Student / Recruiter│        │   Auth, CRUD, jobs,    │        │  users, jobs,         │
│  / Admin dashboards │        │   orchestration,       │        │  applications,        │
└───────────────────┘        │   audit logging        │        │  audit_logs, etc.     │
                              └──────────┬────────────┘        └─────────────────────┘
                                          │  internal REST
                                          ▼
                              ┌──────────────────────┐
                              │   Python ML Service    │
                              │   (FastAPI)            │
                              │  - Resume parsing       │
                              │    (spaCy NER)          │
                              │  - Embeddings            │
                              │    (Sentence-            │
                              │     Transformers)        │
                              │  - Ranking model          │
                              │    (scikit-learn)         │
                              │  - Explanation & skill-gap │
                              │    generation (LLM)        │
                              └──────────────────────┘

Principle: ML service is stateless — it receives text/vectors, returns scores/explanations. Node + Mongo remain the single source of truth. This keeps the ML service easy to scale, retrain, or swap independently.

Addition: Redis cache. Sits behind the ML service, caching embeddings (keyed on resumeId/jobId + modelVersion) and LLM-generated explanations (keyed on applicationId + modelVersion). Without it, every score/explain call recomputes or re-calls the LLM even when nothing changed — wasteful and slow, especially for /explain, which is the highest-latency call in the pipeline. Recompute only fires when a resume, JD, or model version actually changes.

GET    /api/admin/audit-logs
GET    /api/admin/analytics

4.2 Python ML Service (FastAPI) — key endpoints

POST /parse-resume        { resumeText }               → parsed entities (skills, edu, exp)
POST /embed                { text }                     → vector
POST /score                { jdText, resumes: [...] }   → ranked list + feature breakdown
POST /explain               { jd, resume, features }     → LLM-generated explanation
POST /skill-gap             { studentProfile, jobOrRole } → missing skills + resources
POST /simulate               { studentProfile, hypotheticalSkills, target } → projected score delta

Keep /score fast (embeddings + sklearn only); route /explain and /skill-gap through the LLM as separate, cacheable calls so recruiters aren't waiting on LLM latency just to see a ranked list.

5. AI Shortlisting Pipeline

  1. Hard filters (Node/Mongo query — no ML): CGPA cutoff, branch, backlogs, batch year.
  2. Resume parsing (spaCy NER): extract skills, education, experience, projects from resume text.
  3. Semantic matching (Sentence-Transformers): embed JD and resume/skill sections, cosine similarity score.
  4. Ranking model (scikit-learn): combine semantic score + skill overlap %
    • CGPA fit + experience relevance into a final score. Start with a weighted formula; retrain on real accept/reject labels once available.
  5. Explanation layer (LLM): generate a human-readable rationale citing only matched/missing evidence — no invented claims.

6. MongoDB Schema

// users
{ _id, email, passwordHash, role: "student"|"recruiter"|"admin", isVerified, createdAt }

// students
{
  _id, userId, name, rollNumber, branch, batch, cgpa, backlogs,
  resumeUrl, resumeText,
  parsedProfile: {
    skills: [String],
    experience: [{ title, org, duration, description }],
    education: [{ degree, institute, year }],
    projects: [{ title, description, techStack }]
  },
  embeddings: { vector: [Number], modelVersion }
}

// recruiters
{ _id, userId, companyName, companyLogoUrl, website, verified }

// jobs
{
  _id, recruiterId, title, description, jdText,
  skillsRequired: [String],
  eligibility: { minCgpa, branches: [String], maxBacklogs, batch },
  ctc, location, deadline, status: "open"|"closed",
  jdEmbedding: { vector: [Number], modelVersion }
}

// applications
{
  _id, jobId, studentId,
  status: "applied"|"shortlisted"|"interview"|"offered"|"rejected",
  aiScore: {
    finalScore: Number,
    featureBreakdown: [{ feature, value, weight }],
    matchedSkills: [String],
    missingSkills: [String],
    explanation: { summary: String, modelVersion: String },
    scoredAt: Date
  },
  appliedAt,
  statusHistory: [{ status, changedAt, changedBy }]
}

// skill_gap_reports
{
  studentId, targetJobId, // or targetRole for aggregate mode
  currentSkills: [String], requiredSkills: [String], missingSkills: [String],
  recommendations: [{ skill, resourceType, title, url }],
  generatedAt
}

// audit_logs (append-only)
{
  entityType, entityId,
  action: "ai_scored"|"recruiter_shortlisted"|"recruiter_rejected"|"recruiter_overrode_ai"|"status_changed",
  actor: { type: "system"|"user", userId, role },
  before, after,
  reason: String,          // required on override
  aiScoreAtTimeOfAction: Number,
  timestamp
}

Indexes: applications{jobId,status}, students{branch,cgpa,batch}, jobs{status,deadline}.

Scale note: raw vector arrays in Mongo are fine up to a few thousand students. Beyond that, migrate to Atlas Vector Search for the embedding similarity step instead of computing cosine similarity in Python.

7. Explainability, Skill-Gap & What-If Simulation

  • Explainability: every aiScore carries a featureBreakdown (cheap, deterministic) plus an LLM summary (cached, not regenerated per view). If/when the sklearn model is trained on real labels, add SHAP values for true per-prediction attribution.
  • Skill-gap analysis: reuses missingSkills from scoring. Support both per-job ("why you weren't a top match here") and aggregate mode (most common missing skills across a target role category).
  • What-if simulation: re-runs scoring with a hypothetical skill set added to the student's profile — no new resume parsing needed. Keep it stateless/on-demand unless you want engagement analytics.

8. Human-in-the-Loop & Audit Trail

  • AI never finalizes a decision — it ranks and recommends only.
  • Every state change (AI score, recruiter shortlist/reject, status change) writes an immutable audit_logs entry.
  • Overriding the AI's top recommendation requires a reason (dropdown + free text). This is both the fairness/compliance trail and labeled training data for future model retraining.
  • Admin dashboard can compute shortlist-rate breakdowns (branch, category, etc.) directly from this log without any redesign.

10. Build Roadmap

Build bottom-up: data model → plain CRUD → ML pipeline → intelligence features → polish. Each phase should leave you with something runnable, not a half-finished layer.

Phase 0 — Setup (few days)

  • Repo structure: client/ (React), server/ (Node), ml-service/ (Python)
  • MongoDB Atlas cluster + connection from Node
  • Cloudinary account + upload test
  • Env config for all three services, .env conventions agreed early

Phase 1 — Auth & core CRUD (Node + Mongo)

  • User model + JWT auth (register/login/refresh) for all three roles
  • Student profile CRUD, Recruiter profile CRUD
  • Job posting CRUD (recruiter creates/edits/closes jobs)
  • Basic role-guarded routes (middleware checking role on each request)
  • Checkpoint: a recruiter can post a job, a student can view it — no ML yet.

Phase 2 — Resume pipeline

  • Resume upload → Cloudinary, store URL on student profile
  • Text extraction (pdfplumber/PyMuPDF) in the Python service
  • spaCy NER to populate parsedProfile (skills, education, experience)
  • Let students review/edit parsed data — don't trust extraction blindly
  • Checkpoint: uploading a resume populates a structured profile the student can see and correct.

Phase 3 — Matching & shortlisting (the core ML loop)

  • Hard filters in Node (CGPA, branch, backlog, batch) — plain Mongo query
  • /embed endpoint: Sentence-Transformers embeddings for JD + resumes
  • /score endpoint: cosine similarity + weighted formula → finalScore
  • Application flow: apply → status pipeline → recruiter sees ranked list
  • Checkpoint: recruiter can post a job, see a ranked shortlist with a numeric score, and move applications through statuses manually.

Phase 4 — Audit logging

  • audit_logs collection, written on every AI score event and every status change
  • Enforce mandatory reason when a recruiter's decision overrides the AI's top-ranked candidates
  • Do this now, not later — retrofitting audit logs onto an existing flow is much more error-prone than building it in from the start
  • Checkpoint: every action in Phase 3's flow now has a queryable history.

Phase 5 — Explainability

  • /explain endpoint: LLM call with JD + resume + feature breakdown, constrained prompt (cite only matched/missing evidence, no invention)
  • Redis cache keyed on applicationId + modelVersion so explanations aren't regenerated on every page view
  • Surface featureBreakdown (deterministic, free) and summary (LLM-generated, cached) in the recruiter's ranked list view
  • Checkpoint: every score has a "why" a recruiter can read without waiting on a fresh LLM call.

Phase 6 — Skill-gap analysis

  • /skill-gap endpoint reusing missingSkills already computed in scoring
  • Per-job mode first (simpler), then aggregate mode across a role category
  • Static curated skill → resource mapping (don't build a recommender yet)
  • Checkpoint: a rejected/low-scoring student sees concretely what skills to work on.

Phase 7 — What-if simulator

  • /simulate endpoint: re-run scoring with a hypothetical skill set added
  • Simple UI: toggle/add skills, see projected score change live
  • Stateless — no persistence needed unless you want engagement analytics
  • Checkpoint: students can experiment with "what if I learned X" and see the score delta immediately.

Phase 8 — Admin dashboard & analytics

  • Placement analytics (branch-wise, CGPA-band placement rates)
  • Audit log viewer with filters
  • Fairness dashboard: shortlist rates sliced by branch/category, computed straight from audit_logs
  • Model version display (which scoring model is live)

Phase 9 — Polish & hardening

  • Retrain the scikit-learn ranking model on real shortlisting_feedback labels if you've accumulated enough recruiter decisions; add SHAP values for per-prediction attribution if you do
  • Rate limiting, input validation, error handling across all three services
  • Loading states, empty states, and mobile responsiveness on all dashboards
  • Basic test coverage on the scoring pipeline especially — it's the part most likely to silently regress

Rule of thumb: don't start Phase N+1 until Phase N's checkpoint actually works end-to-end. It's tempting to build the what-if simulator because it's the flashy part, but it's useless without a working scoring pipeline underneath it.
